# 나의 이름은 — MVP 제품 기획 확정

작성일: 2026-09-29

상태: **Accepted — 제품 기획 확정, 구현 전.** 승인 근거: 2026-09-29 사용자 추천안 승인 및 자율 확정 위임. Q1(이름 부분 등급·성씨 별도), Q2(3단계 조건표), Q3(초기 한자 검토 목표 200자·오행별 40자)를 포함한다. 명리 개별 조건표와 검토 데이터의 미완성은 승인으로 해소되지 않으며 §8의 출시 선행 작업이다.

## 1. 제품의 질문

“이 이름으로 살아왔다면, 내 지난날은 어떻게 달랐을까?”

사용자는 출생정보와 현재 이름을 입력한다. 현재 이름을 짧게 평가받고, 균형형과 극대화형의 새로운 이름 및 그 이름으로 살았을 법한 과거의 회상문을 읽는다. 모바일 웹을 우선하며 태블릿·PC에서도 이용한다.

이용 대상에 나이 제한을 두지 않는다. 성인뿐 아니라 영유아·어린이·청소년의 출생정보와 이름도 승인된 입력 범위 내에서 분석할 수 있다. 만 19세 이상으로 한정하는 제안은 채택하지 않았다.

## 2. 확정된 사용자 흐름

1. 출생정보와 현재 이름 입력. 성씨와 이름은 별도 입력 칸으로 받으며, 전체 이름에서 성씨 경계를 자동 추정하지 않는다. 한글 이름은 필수, 한자는 선택이다.
2. 성씨 칸과 이름 칸 각각의 음절에 대응하는 한자를 고르는 선택기를 제공한다. 휠 형태와 검색 가능한 접근성 선택기를 제공한다(§9).
3. 이름 분위기를 선택한다: 남성적 / 여성적 / 중성적 / 상관없음. 기본값은 상관없음이며 두 추천 유형에 공통 적용한다.
4. 현재 이름을 사주 균형 기준으로 짧게 평가한다. 단계는 잘 맞는 이름 / 일부 보완할 이름 / 보완이 필요한 이름이다. 정보 부족에 따른 판단 보류는 별도로 표시한다.
5. ‘좋은 이름 확인하기’를 누르면 균형형 이름과 한글·한자·뜻·추천 근거·회상문을 본다.
6. ‘나의 장점을 극대화하는 이름’을 선택하면 극대화형의 동일 구성 결과를 본다.
7. 각 유형에서 공개된 다른 후보를 볼 수 있다.
8. ‘친구한테 보내기’로 카카오톡에 서비스 시작 URL을 전달한다. 친구는 자신의 정보를 입력한다. 공유 URL에는 원 사용자의 입력·결과를 포함하지 않는다.

현재 이름이 이미 균형에 잘 맞으면 이를 인정한다. 다른 뜻과 소리로 같은 균형을 담은 대안을 제시하며, 회상문은 더 나은 과거를 강요하지 않고 다른 가능성을 표현한다.

사용자는 한자를 입력하지 않은 현재 이름에 A(소리 기준의 부분 풀이)를 적용하기로 확정했다. 순한글 이름과 한자를 모르는 이름 모두 발음오행으로 확인할 수 있는 내용만 설명하고, 이름 전체의 ‘잘 맞는 이름 / 일부 보완할 이름 / 보완이 필요한 이름’ 등급은 붙이지 않는다. 한자 미입력 자체는 감점 사유가 아니다. 사주 분석과 후보 조건을 충족하면 새 한자 이름 추천은 그대로 제공한다. 안내 예: ‘한자 없이도 이름의 소리는 살펴볼 수 있어요. 지금은 소리를 기준으로 풀이하고, 새로운 이름은 사주에 맞춰 제안해 드릴게요.’ 실제 추천이 보류되는 경우에는 추천 가능성을 확정적으로 안내하지 않는다.

일부 음절만 한자를 입력한 경우에도 부분 풀이를 제공하기로 사용자 확정했다. 입력한 한자는 확인된 뜻·자원오행만 설명하고, 한글 전체에는 초성 기준의 발음오행 풀이를 제공한다. 성씨 또는 이름의 한자가 하나라도 빠지면 이름 전체의 3단계 평가는 하지 않는다. 수리 계산에 필요한 획수를 모두 확인할 수 없으면 수리 풀이도 생략한다. 새 이름 추천은 확인 가능한 조건으로 진행하며 모르는 한자를 임의로 채우지 않는다. 예를 들어 ‘김민수’에서 ‘민’의 한자만 입력했다면 해당 글자의 확인된 뜻은 보여주되 전체 이름이 좋거나 나쁘다고 판정하지 않는다.

입력 길이는 한글 성씨 1~2글자, 현재 이름 1~5글자로 제한한다. 추천 이름 부분은 현재 이름의 길이와 관계없이 두 글자다.

수리 풀이의 길이 범위는 사용자 확정 사항이다. 성씨 1~2글자·이름 부분 1~2글자이며 계산에 필요한 한자와 획수가 모두 확인된 경우에만 제공한다. 이름 부분이 3~5글자이면 수리 풀이를 제공하지 않지만, 확인 가능한 뜻·자원오행·발음오행 풀이와 새 이름 추천은 계속 지원한다. 수리 풀이 미지원 자체로 감점하지 않는다. 추천 이름은 두 글자이므로 성씨 한자와 필요한 획수까지 확인되면 이 길이 범위에 들어간다. 원획수·수리표 채택 정책과 미검증 범위는 핵심 규칙 문서에 따른다.

## 3. 확정된 추천 원칙

- 팔자 글자의 오행 개수만으로 판단하지 않는다. 계절과 오행 간 관계 등 사주 구조를 분석해 필요한 기운을 판단한다. 실행 계약과 자료 채택은 핵심 규칙 문서를 따르며 개별 조건표 검토는 출시 선행 작업이다.
- 균형형은 분석에서 필요한 것으로 판단한 오행을 보완하는 방향이다.
- 균형형의 두 한자 구성은 A로 사용자 확정했다. 최소 한 글자의 자원오행은 최종 목표 오행이어야 하고, 나머지 한 글자도 해당 사주 분석에서 보완에 적합하다고 명시적으로 허용된 오행이어야 한다. 목표 오행 두 글자도 허용한다. 예를 들어 목표가 화이고 목도 허용된 경우 화·화 / 목·화 / 화·목을 후보로 허용한다. 목표를 생하는 오행이라는 이유만으로 다른 오행을 자동 허용하지 않는다. 목표 오행이 두 글자라는 이유만으로 한 글자인 조합보다 우선하지 않으며, 통과한 후보에는 아래 공통 추천 순서를 적용한다.
- 극대화형의 대상은 팔자 글자 수가 가장 많은 오행이 아니라, 계절·통근·다른 기운의 도움과 제약 등 사주 구조상 가장 강한 오행이다. 이를 의도적으로 더 강화한다. 과도하게 강한 경우에도 이 방향을 유지하고 회상문에 특성과 부담을 함께 담는다. 균형형보다 더 좋은 이름이라는 순위는 붙이지 않는다. 다섯 오행의 강도를 비교하는 구체적인 규칙은 추가로 확정·검증해야 하며, 기존 일간 강약 판정을 그대로 대체 사용하지 않는다.
- 공동으로 가장 강하다고 판정된 오행이 여러 개면, 그 오행들 중 **화 → 수 → 목 → 토 → 금** 순서로 하나를 선택해 극대화형의 목표로 삼는다. 이는 서비스의 동률 처리 규칙이며 명리학의 보편적인 오행 우열을 뜻하지 않는다. 단독 최강 판정에는 이 우선순위를 적용하지 않는다. 판정 근거 부족이나 시간 미상 후보 사이의 추천 방향 불일치를 이 규칙으로 해소하지 않으며, 해당 경우의 보류 정책을 유지한다.
- 극대화형의 두 한자 구성은 추천안 A로 사용자 확정했다. 두 글자의 자원오행 모두 위 절차에서 선정한 최강 오행이어야 한다. 예를 들어 목표가 화라면 화·화로 구성하며, 목표를 생하는 다른 오행으로 대체하지 않는다. 이 조건을 충족하는 후보가 부족하면 확보한 수만 제공하고, 없으면 해당 유형을 보류한다. 이 구성은 서비스의 강화 방향을 표현하는 규칙이며 이름의 실제 효과를 입증한 것으로 설명하지 않는다.
- 한자의 자원오행을 추천의 중심 기준으로 사용한다. 발음오행은 보조 기준, 원획수·81수리는 계산에 필요한 한자가 확인된 경우의 참고 풀이로 사용한다.
- 발음오행은 표기된 한글의 각 음절에서 초성만 추출한다. 성씨와 이름 모두 같은 방식을 적용한다. 사용자는 받침 포함 방안을 검토한 뒤 초성만 사용하는 것으로 확정했다. 중성·종성 및 연음 등 실제 발음 변화는 반영하지 않는다.
- 초성의 오행 배속표도 사용자 확정: 목=ㄱ·ㅋ·ㄲ, 화=ㄴ·ㄷ·ㄹ·ㅌ·ㄸ, 토=ㅇ·ㅎ, 금=ㅅ·ㅈ·ㅊ·ㅆ·ㅉ, 수=ㅁ·ㅂ·ㅍ·ㅃ. 기존 구현과 같은 표를 서비스 기준으로 채택하며, 문헌별 차이가 있는 배속을 보편적인 정답이라고 표시하지 않는다.
- 음절 간 상생 관계는 A(글자 순서와 무관하게 인정)로 사용자 확정했다. 목–화, 화–토, 토–금, 금–수, 수–목 조합은 양쪽 순서 모두 상생 관계로 인정한다. 이는 이름에서의 관계 평가이며 생하는 방향 자체를 뒤집어 설명하지 않는다.
- 비교 범위는 성씨와 이름을 순서대로 이어 붙인 전체 이름의 이웃한 음절이다. ‘김하늘’은 김–하, 하–늘을 비교한다. 복성 및 긴 현재 이름에도 같은 규칙을 적용하고 비인접 음절은 이 비교에 포함하지 않는다. 같은 오행끼리는 상생과 구분해 ‘동일 오행’으로 표시한다.
- 사용자는 발음오행 상극 처리의 추천안 A를 확정했다. 상극이 있어도 후보를 자동 탈락시키지 않는다. 사주 적합성과 자원오행 조건을 먼저 충족하고, 나머지 조건이 같은 후보끼리는 이웃한 음절의 상극 관계 수가 적은 이름을 우선한다. 현재 이름의 풀이에서도 상극만으로 이름 전체를 나쁘다고 단정하지 않는다. 아래 공통 추천 순서를 적용한다.
- 수리의 길흉만으로 이름 전체를 나쁘다고 판정하거나 후보를 반드시 탈락시키지 않는다.
- 한자가 없다는 이유로 감점하지 않는다. 확인되지 않은 한자·오행을 임의로 채우지 않는다.
- 추천은 한자 이름으로 한정한다. 기존 성씨를 유지하고, 새 이름 부분은 두 글자로 고정한다. 현재 이름의 길이 지원 범위와는 별개다.

후보 탐색 순서:

1. 사주 분석으로 추천 유형별 목표 오행을 정한다.
2. 뜻·독음·자원오행의 근거가 확인된 한자로 목표에 맞는 조합을 찾는다.
3. 성씨를 포함한 전체 이름의 뜻·독음·발음오행 등을 검토한다. 성씨 한자를 모르면 확인할 수 있는 조건만 적용한다.
4. 자연스러움과 사용자가 선택한 분위기를 반영해 순위를 정한다. 검토된 한글 이름 목록은 참고 자료이며 필수 통과 목록이 아니다.
5. 유형별 최대 3개 후보를 확보한다. 실제 후보가 부족하면 확보한 만큼만 제공하고, 적합한 후보가 없으면 추천을 보류한다.

같은 입력·계산 규칙·데이터 버전이면 추천 이름과 순위는 동일하다. ‘다른 이름 보기’는 무작위 재추첨이 아니라 선정된 후보 탐색이다.

조건을 통과한 후보의 공통 추천 순서는 사용자 확정 사항이다. ① 이름으로서의 자연스러움 → ② 사용자가 선택한 분위기와의 일치 → ③ 이웃한 음절의 발음오행 상극 관계 수가 적은 순서 → ④ 한글·한자 기준의 고정 순서로 정렬한다. 앞 기준이 같은 경우에만 다음 기준을 적용한다. 사주·자원오행 조건은 정렬 전에 반드시 충족해야 하며, 자연스러움이나 분위기로 이 조건을 상쇄하지 않는다. 자연스러움과 분위기는 검토된 데이터로 판단하고 실행 시 AI가 순위를 결정하거나 변경하지 않는다. 최종 동률은 NFC 한글 이름 → 원문 한자 코드 포인트 배열의 오름차순 사전식 비교로 해소한다. 로케일별 정렬을 사용하지 않는다.

자연스러움의 판정 방식은 사용자 확정 사항이다. 검토해 자연스럽다고 표시한 한글 이름을 우선하고, 목록 밖 이름도 후보로 허용하되 검토된 이름 다음에 배치한다. 목록은 필수 통과 목록이 아니며, 미검토를 부자연스럽다는 판정으로 사용자에게 표시하지 않는다. 성씨와 합쳤을 때 부적절한 단어가 되는 등 명확한 제외 사례는 별도 목록으로 관리한다. 실행 시 AI 점수화는 하지 않는다. 미검토 후보에는 어색한 이름이 남을 수 있으므로 후보 검토를 통해 데이터를 보완한다. 초기 검토 데이터의 내용은 후속 명세에서 고정한다.

추천 후보의 부적절한 이름 제외 방식도 사용자 확정 사항이다. 이름 부분 또는 성씨를 합친 전체 한글 이름이 해당 제외 목록과 정확히 일치할 때만 이름을 제외한다. 특정 음절의 포함 여부나 한자 뜻풀이 속 특정 단어의 포함 여부로 일괄 제외하지 않는다. 예를 들어 ‘울’이라는 문자열 때문에 뜻풀이가 ‘아름다울’인 한자를 자동 제외하지 않는다. 뜻이나 사용상 문제가 있는 한자는 별도 검토를 통해 해당 한자를 추천 대상에서 제외한다. 정확한 일치 방식으로 포착하지 못한 부적절 사례는 발견 후 목록에 추가한다. 이 목록은 추천 후보의 제외 기준이며 사용자가 입력한 현재 이름의 좋고 나쁨을 판정하는 기준으로 사용하지 않는다.

분위기의 판정 방식도 사용자 확정 사항이다. 이름에 검토된 남성적·여성적·중성적 태그를 부여하며 복수 태그를 허용한다. 자연스러움 등급이 같은 후보끼리는 사용자가 선택한 태그가 있는 이름을 우선한다. 선택한 태그가 없는 다른 분위기의 이름과 미분류 이름은 모두 제외하지 않고 분위기 기준상 같은 후순위로 둔다. ‘상관없음’을 선택하면 분위기 기준을 건너뛴다. 미분류를 중성적으로 자동 분류하지 않으며, 태그는 이름의 인상에 관한 분류로만 사용한다. 실제 초기 태그 데이터는 별도 검토가 필요하다.

현재 이름 및 유형 내 중복 제외는 사용자 확정 사항이다. 한자 조합이 달라도 추천 이름의 한글이 현재 이름과 같으면 제외한다. 각 추천 유형 안에서도 한글이 같은 후보는 위 공통 추천 순서에서 가장 높은 순위의 한자 조합 하나만 남겨, 최대 3개가 서로 다른 한글 이름이 되도록 한다. 성씨는 유지하므로 비교 대상은 이름 부분이다. 중복 제거 후 적합한 후보가 부족하면 확보한 수만 제공하며 중복으로 개수를 채우지 않는다.

유형 간 중복 제외도 사용자 확정 사항이다. 균형형의 최대 3개 후보를 먼저 확정하고, 극대화형에서는 그 후보들과 한글이 같은 이름을 제외한 뒤 다음 순위의 적합한 후보를 선택한다. 대체 후보가 부족하면 개수를 줄이며 추천 조건을 완화하지 않는다. 이 처리는 관리자 노출 개수와 관계없이 최대 3개 후보를 선정하는 단계에서 수행하고, 이후 노출 설정을 적용한다. 따라서 비공개 균형형 후보도 극대화형의 중복 제외 대상이다. 균형형을 확정할 수 없어 후보가 없으면 해당 유형 때문에 제외할 이름도 없다.

## 4. 시간 미상과 불확실성

### 확정: 균형형의 방법 간 합의 원칙

사용자는 2026-09-29 세부 규칙 논의에서 A(여러 판단의 합의)를 유지하기로 확정했다. 억부·조후·통관·병약 중 어느 한 방법을 무조건 우선하지 않는다. 각 방법의 적용 여부와 판단 근거를 먼저 확인하고, 적용되는 판단들이 양립하는 방향만 균형형 목표 후보로 남긴다.

- 한 판단의 허용 후보가 목·화이고 다른 판단의 허용 후보가 화라면, 화를 공통 후보로 남긴다. 이 예시는 방법 간 합의 처리이며 실제 사주 판정표를 대신하지 않는다.
- 적용되는 판단들의 허용 방향이 충돌하고 공통 후보가 없으면 균형형을 보류한다.
- 필요한 판단을 계산하지 못한 상태를 ‘적용할 필요 없음’이나 합의로 처리하지 않는다. 필요한 판단이 미지원·정보 부족이면 균형형을 보류한다.
- 공통 후보가 있다는 사실만으로 최종 목표를 확정하지 않는다. 원국에서 해당 방향을 사용할 수 있는지에 대한 명시적인 선택 조건을 통과해야 한다.
- 각 방법의 적용·비적용, 허용 집합과 최종 선택 계약은 핵심 규칙을 따른다. 실제 개별 조건표는 출시 전 검토한다. 이 결정은 해당 계산의 구현 완료를 뜻하지 않는다.

### 입력과 후보 간 불확실성

사용자는 일간의 강약을 확정하지 못하면 균형형 추천을 보류하기로 확정했다. 강약 미확정을 ‘균형이 좋은 사주’로 처리하지 않는다. 극대화형은 구조상 최강 오행의 확정 여부를 별도로 판단한다. 사용자는 보류 화면을 ‘이유 설명 → 확인된 내용 → 가능한 다음 행동’으로 구성하고, 아래 상황별 행동과 버튼 우선순위를 적용하기로 확정했다.

확정된 보류 안내:

- 공통: ‘현재 분석 기준으로는 균형을 보완할 방향을 하나로 정하기 어려워요. 이름이 나쁘다는 뜻은 아니에요.’ 확인된 사실과 해당 결과의 보류 이유를 짧게 보여준다. 균형 판단에 의존하는 현재 이름의 3단계 평가도 함께 보류한다.
- 시간 미상으로 가능한 원국의 방향이 갈리는 경우: 정확한 시각을 알 때만 ‘출생시간 추가하기’를 제공한다. 모르면 입력을 강요하지 않으며, 시각을 추가해도 추천이 반드시 가능해진다고 약속하지 않는다.
- 정확한 정보에서도 분석 기준이 충돌하는 경우: 입력 수정을 해결책처럼 유도하지 않는다. 극대화형이 확정됐다면 ‘나의 강점을 담은 이름 보기’로 연결하고, 균형형과 목적이 다르다는 설명을 붙인다.
- 두 유형 모두 보류인 경우: 현재 입력에서 확인된 독음·한자 뜻과 발음 등 확인 가능한 정보만 제공한다. 한자가 없거나 뜻이 검토되지 않았다면 해당 풀이를 만들어내지 않는다. 추천 이름에 의존하는 회상문은 생성하지 않는다. 정보 수정과 서비스 공유는 계속 가능하다.
- 보류 결과는 정상적인 분석 상태로 표현한다. 통신·계산 실패와 구분하고, 동일 입력으로 반복 실행하도록 유도하지 않는다.

확정된 다음 행동과 버튼 우선순위:

- 시간 미상으로 보류된 경우의 주 행동은 ‘출생시간 추가하기’다. 정확한 시간을 모르면 추가를 강요하지 않는다.
- 정확한 출생정보에서도 균형형이 보류되고 극대화형은 가능한 경우의 주 행동은 ‘나의 강점을 담은 이름 보기’다.
- 두 유형 모두 보류된 경우의 주 행동은 ‘지금 이름 살펴보기’다. 확인 가능한 이름 정보가 부족하면 한자 추가나 입력정보 확인을 안내하며 빈 풀이를 만들어내지 않는다.
- 한자가 미입력인 경우 ‘내 이름의 한자 추가하기’를 통해 뜻·성명학 풀이를 보완할 수 있다. 한자 추가는 사주 자체의 판단 보류를 해결하는 행동으로 설명하지 않는다. 순한글 이름에는 한자 입력을 강요하지 않는다.
- ‘입력정보 확인하기’와 ‘친구에게 보내기’는 하단 보조 행동으로 제공한다. 정보 확인에서는 생년월일·양음력·지역 등 실제 입력을 수정할 수 있고, 공유는 개인정보 없는 서비스 시작 URL을 사용한다.
- 모든 버튼을 동시에 나열하지 않고 상황에 맞는 주 행동 하나와 필요한 보조 행동을 표시한다.

- MVP의 출생지역은 국내로 한정한다. 해외 출생은 지원하지 않는다. 국내 지역은 기존 locations.ts의 kma-2026-07-01-v1 목록을 채택한다(§9).
- 출생일의 제품 지원 범위는 1900년 1월 1일부터 이용 당일(오늘)까지이며 미래 출생일은 허용하지 않는다. 양력 환산일 기준 경계·KST 오늘·미래시각 검증은 §9에 따른다. 공급자·엔진 지원은 출시 전 실제 확인한다. 기존 엔진 문서의 검증 범위는 2026년까지이므로 이후 연도로 넘어가는 운영 조건을 별도로 확인해야 한다.
- 생년월일은 양력과 음력 모두 지원하며 양력을 기본 선택한다. 음력을 선택하면 평달·윤달을 선택한다.
- 출생시각 입력은 ‘정확한 시·분’과 ‘시간 모름’ 두 가지로 한정한다. 대략적인 시간만 아는 경우에는 ‘시간 모름’으로 진행하도록 안내하며, 대략적 시각이나 시간 범위 입력은 MVP에서 제공하지 않는다.
- 가능한 사주 후보들의 추천 방향이 공통이면 추천하고, 방향이 갈리면 해당 추천을 보류한다.
- 균형형과 극대화형의 제공 가능 여부를 각각 판단한다.
- 출생정보가 정확하더라도 채택한 분석 기준의 충돌 등으로 추천 방향을 확정할 수 없으면 해당 유형의 추천을 보류한다. 균형형만 보류이고 극대화형은 확정이면 극대화형을 제공하며, 반대의 경우도 동일하게 처리한다. 두 유형 모두 보류이면 확인된 사주 정보와 짧은 보류 이유를 보여주고 이름을 임의로 추천하지 않는다.
- 안내 문구 예: ‘균형을 보완하는 방향이 여러 갈래로 나뉘어, 지금은 하나의 이름으로 추천하기 어려워요.’ 극대화형의 화 → 수 → 목 → 토 → 금 우선순위는 공동 최강 선택에만 적용하며 분석 기준 충돌을 덮는 용도로 사용하지 않는다.
- ‘방향이 공통’은 모든 실제 가능한 완전 원국에서 목표가 확정·일치하고 추천 조합도 공통으로 허용됨을 뜻한다. 현재 이름 등급·근거도 후보 간 일치해야 하며 핵심 규칙의 합의 계약을 따른다.

## 5. 회상문

AI는 확정된 분석과 이름을 바탕으로 문장을 작성한다. 이름의 평가·선정·명리 재계산을 맡지 않는다. 외부 AI에는 출생일시 원문 대신 필요한 분석 요약과 이름·뜻을 전달하는 구성으로 진행한다.

회상문 생성 제공자는 DeepSeek, API 모델명은 `deepseek-flash`로 확정한다. 추론 모드는 명시적으로 끈다. 이는 비용 검토에 따른 채택이며 한국어 문체·품질 검증 완료를 뜻하지 않는다. 모델의 응답 검증과 실패 처리는 별도로 구현한다.

2026-09-29 확인한 [공식 요금표](https://api-docs.deepseek.com/quick_start/pricing/) 기준 Flash의 혼잡 시간대 요금은 100만 토큰당 입력 캐시 미적중 $0.30, 출력 $1.20이며 비혼잡 시간대는 절반이다. [공식 추론 모드 안내](https://api-docs.deepseek.com/guides/thinking_mode/)에 따르면 추론 모드는 기본으로 켜져 있으므로 요청 시 비활성화를 명시해야 한다.

예산 추정은 회상문 1개당 입력 2,000토큰·출력 600토큰, 캐시 할인 없이 혼잡 시간대 요금으로 계산했다. 1개당 $0.00132, 양쪽 유형의 최대 6개를 모두 생성하면 사용자당 $0.00792다. 같은 이용자 1만 명이면 $79.20이며, 가정 환율 1달러=1,400원에서 110,880원이다. 토큰량은 실측 전 가정이며 현재 환율을 확인한 값이 아니다. 서버 비용·세금·결제 수수료·재시도 비용은 제외한다. 이 추정은 이용량 제한이나 지출 상한이 아니며 운영 예산·제한은 별도로 정해야 한다. 실제 배포 전 요금과 모델 제공 상태를 재확인한다.

문체: 아쉬웠을 법한 순간 → 이름에 담긴 특성 → 달라졌을지도 모를 과거. 사용자의 실제 과거 사건을 알고 있는 것처럼 단정하지 않고 ‘그랬을지도’, ‘그러지 않았을까요’로 기억을 대입할 여지를 준다.

연령 제한이 없는 제품에 맞춰 회상문의 장면을 조절한다: AI에는 원본 생년월일 대신 서버가 계산한 연령대를 전달한다. 어린이·청소년에게 성인의 직장·결혼 등 경험을 전제하지 않고, 영유아에게 긴 과거의 후회나 놓친 기회를 꾸며내지 않는다. 영유아는 이름이 불리는 순간의 느낌처럼 짧은 과거에도 성립하는 가상 장면을 중심으로 한다. 분석일 KST 날짜와 양력 환산 생일로 계산한 만 나이 기준 0~5세 / 6~12세 / 13~18세 / 19세 이상을 채택한다. 각각 이름을 부르는 목소리·놀이·돌봄 / 놀이·배움·친구 / 관심사·도전·관계 / 선택·일상·관계의 가상 장면을 쓴다. 성인에게도 취업·결혼·출산을 실제 경험으로 전제하지 않는다. 어린 연령의 첫 문단은 큰 후회 대신 작은 망설임이나 다른 가능성을 담는다. 저장된 연령대와 문장은 생일이 지나도 자동 변경하지 않는다.

승인된 톤의 예시이며 모든 사람에게 적용하는 고정 해설은 아니다:

> 그때 하고 싶은 말을 조금 더 차분하게 전할 수 있었을지도 몰라요. 마음이 앞서 서둘렀던 순간에도, 한 번 더 생각하고 내게 맞는 길을 골랐을 테니까요. 이 이름으로 살아왔다면, 나를 다그치기보다 내 속도를 믿는 날이 조금 더 많지 않았을까요.

> 마음속에만 품었던 일을 조금 더 일찍 시작했을지도 몰라요. 남들의 반응을 살피다 접어둔 생각을 끝까지 밀어붙였다면, 지금쯤 내 이름으로 남긴 무언가가 있었을 수도 있겠죠. 그만큼 부딪히는 일도 많았겠지만, 해보지 못했다는 아쉬움은 조금 덜했을 거예요.

회상문은 해당 이름을 처음 열 때 생성한다. 완성된 문장은 브라우저에 저장해 다시 보여준다. 기록을 삭제하고 새로 생성하면 표현은 달라질 수 있다. 성공한 회상문은 재생성하지 않으며 재생성 버튼도 제공하지 않는다.

이름 추천이 완료되면 추천 이름·뜻·계산 근거를 먼저 보여주고 새 결과를 저장한다. AI 회상문 생성 실패는 이름 추천의 실패로 취급하지 않는다. 실패한 회상문 영역에 ‘다시 불러오기’를 제공하고, 성공한 회상문은 해당 결과에 추가 저장한다. 회상문 재시도로 추천 이름이나 순위를 바꾸지 않는다. 새 분석으로 결과가 교체된 뒤 도착한 이전 분석의 회상문이 새 결과에 붙지 않도록 구분해야 한다.

### 회상문 JSON 계약과 이용량 제한 설계

사용자 확정: 월 10만 원을 기준으로 이용량 제한을 설계하고, 요청을 구조화하며 응답 형식과 문장 길이를 제한한다. 아래 수치는 자율 확정 위임으로 채택한 최초 운영 설정이다. 실측 후 변경은 근거·버전을 기록한다. 모델 호출·예산 집행 기록은 아니다. 요청·실패·재시도·중복의 정규 계약은 [API 계약](2026-09-29-my-name-is-api-contract.md)에 둔다.

- 한 요청은 추천 이름 하나의 회상문만 생성한다. 이름·뜻·평가·추천 근거는 서버 계산 결과에서 제공하며 AI가 새로 선택하지 않는다.
- 서버의 시스템 지시와 사용자 데이터 메시지를 분리한다. 사용자 메시지의 데이터는 서버에서 검증한 추천 유형, 추천 이름과 한자 뜻, 목표 오행과 분석 근거 요약, 현재 이름의 평가 상태, 서버가 산출한 연령대를 JSON 문자열로 전달한다. 출생일시 원문과 불필요한 신원 정보는 전달하지 않는다. 데이터 안의 문구를 지시로 취급하지 않는다.
- 요청에는 `model: "deepseek-flash"`, `thinking: {"type":"disabled"}`, `response_format: {"type":"json_object"}`, `max_tokens: 1024`를 명시한다. 시스템 지시에도 JSON으로만 반환하라고 명시한다.
- 응답 구조는 `{ "paragraphs": ["첫 문단", "둘째 문단", "셋째 문단"] }`로 한정한다. 추가 키를 허용하지 않으며 배열은 문자열 3개여야 한다.
- 각 문단은 한 문장을 목표로 40~100자, 총 120~300자다. 글자 수는 문자열 NFC 정규화와 앞뒤 공백 제거 후 Unicode 코드 포인트 수로 센다. 문단 내부의 공백·문장부호는 포함하고 JSON 문법·문단 사이 표시용 줄바꿈은 제외한다. 문단 내 줄바꿈은 허용하지 않는다.
- 첫 문단은 아쉬웠을 법한 순간, 둘째 문단은 이름의 특성이 반영된 다른 선택, 셋째 문단은 달라졌을지도 모를 과거의 여운을 담는다. 극대화형은 과해질 때의 부담도 담으며 현재 이름이 좋은 경우에는 기존 삶보다 반드시 낫다고 표현하지 않는다.
- 회상형 존댓말과 가정 표현을 사용한다. 실제 과거의 사건을 알고 있다고 단정하거나 이름 때문에 특정 결과가 반드시 생긴다고 서술하지 않는다. 분석 요약에 없는 명리 판정이나 이름 의미를 만들어내지 않는다.
- 서버는 JSON 파싱·키·자료형·문단 수·글자 수·완료 상태를 검증한다. JSON 모드는 이 스키마나 문장의 근거 일치까지 자동 보장하지 않는다. 의미 일치와 문체는 별도의 기준 사례 평가가 필요하다. 길이 초과나 `finish_reason=length` 응답을 단순 잘라 성공 처리하지 않는다.
- 입력은 시스템 지시와 데이터·수정 지시를 모두 포함해 요청당 최대 3,000토큰으로 제한한다. 실제 모델 토크나이저에 맞는 계수 방법은 구현 전에 확인한다. 초과 시 검증된 요약을 축약하거나 요청을 거절하며 핵심 근거를 무작정 잘라내지 않는다.
- 실패에 대한 자동 재요청은 하지 않고 사용자 재시도를 1회 허용한다. 모든 재시도도 입력·출력·예산 제한을 동일하게 적용한다. 회상문 실패가 이름 결과를 지우지 않도록 한다.
- 비용 추적은 DeepSeek 응답의 실제 usage를 사용한다. 최초 예산 추정의 입력 2,000·출력 600토큰은 평균 가정이며 위 3,000·1,024토큰은 요청 상한이다. 현재 혼잡 요금과 캐시 미적중 기준으로 요청 1회의 예약 비용 상한은 $0.0021288이다. 재시도는 별도 요청으로 예약한다.
- 확정한 초기 운영값은 한국시간 기준 월 API 사용 한도 $55, 일 한도 $3, 서비스 전체 동시 AI 호출 4개다. 가정 환율 1달러=1,400원에서 월 API 한도는 77,000원으로, 월 10만 원 목표 중 나머지는 환율·세금·수수료 여유분이다. 최종 원화 청구가 정확히 10만 원 이하라는 보장은 아니며 배포 시 실제 환율·결제 조건으로 한도를 재검토한다. 서버 호스팅 비용은 별도다.
- 외부 호출 전에 ‘확정 사용액 + 진행 중 예약액 + 새 요청의 최대 비용’을 원자적으로 검사하고 한도를 넘으면 호출하지 않는다. 정상 응답은 usage로 정산한다. 타임아웃 등 실제 청구 여부를 확인할 수 없는 호출은 예약을 바로 환급하지 않고 보수적으로 유지해 대조한다. 요금 설정은 공식 요금 변경에 맞춰 관리한다.
- 예산 집계와 중복 요청 제어는 클라이언트가 아닌 서버에서 수행한다. 사용자는 비용과 호출 횟수를 보관하는 작은 영속 운영 저장소의 추가를 승인했다. 재배포나 서버 인스턴스 증가로 사용량이 초기화되지 않아야 한다. 날짜별 비용·횟수·단기 요청 상태 등 운영 메타데이터만 보관하며 개인 이름·출생정보·회상문을 영구 보관하는 용도로 사용하지 않는다. 운영 배치와 보존 기간은 백엔드 ADR과 API 계약을 따른다.
- 익명 브라우저 식별만으로 사람별 이용 한도를 확실히 보장할 수 없으므로, 비용 방어 기준은 서버의 전체 일·월 예산이다. 중복 클릭은 같은 생성 작업으로 취급하며 불필요한 중복 과금을 막는다.
- 예산 소진 시 이름·뜻·근거와 저장된 회상문은 계속 보여주고 신규 회상문만 중단한다. 일 한도는 다음 한국시간 날짜, 월 한도는 다음 한국시간 달 시작 이후 생성이 가능하다고 안내한다. 두 한도에 모두 걸렸다면 둘 다 해제돼야 한다.

참고: [DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)의 JSON 출력·max_tokens·완료 상태 계약. 프롬프트만으로 제한을 보장하지 않으며 서버 검증과 비용 집계가 함께 필요하다.

## 6. 구성·저장·관리 설정

- React 기반 Next.js에서 화면과 서버 API를 함께 운영한다.
- 서비스는 개인적인 비상업 실험으로 공개한다. 이 목적에 맞춘 배포안은 Vercel Hobby와 Neon PostgreSQL 무료 플랜이다. 각 무료 사용량 한도 내에서 시작하며 실제 사용량과 배포 시점의 약관·요금을 확인한다. 계정 생성·리소스 연결·배포가 완료된 상태는 아니다.
- Next.js 화면과 서버 API는 Vercel, 영속 운영 저장소는 Neon으로 구성한다. AI 월 10만 원 목표 예산과 호스팅·DB 비용은 구분한다. 상업적 운영으로 목적을 바꾸거나 무료 한도를 넘기는 경우 요금제를 재검토한다.
- 근거(2026-09-29 확인): [Vercel Hobby의 개인·비상업 이용 범위](https://vercel.com/docs/plans/hobby), [Vercel 요금표](https://vercel.com/pricing), [Neon의 Vercel 연동](https://vercel.com/marketplace/neon), [Neon 무료 플랜 안내](https://neon.com/blog/building-patterns-unlocked-by-scale-to-zero). 무료 플랜이 서비스 규모와 무관하게 계속 무료라는 의미는 아니다.
- 명리 엔진·성명학 데이터·추천·AI 호출은 서버가 담당한다. 서버 데이터 전체를 브라우저에 배포하지 않는다.
- 회원가입 없이 이용하며, 개인 입력과 완성된 결과는 사용자 브라우저에 저장한다. 서버에 개인 기록을 영구 보관하지 않는 구성이다.
- 브라우저에는 마지막으로 완료된 한 사람의 입력·결과만 보관한다. 사용자는 정상 완료된 새 분석이라면 추천이 전부 보류여도 기존 기록을 새 입력·결과로 교체하기로 확정했다. 두 유형 모두 제공, 일부 유형만 제공, 두 유형 모두 보류를 모두 완료된 결과로 저장하며 보류 이유와 확인된 내용도 보존한다. 교체는 AI 회상문 완료를 기다리지 않는다. 진행 중이거나 통신·계산·추천 처리 오류로 완료하지 못한 새 분석은 기존 기록을 덮어쓰지 않는다. 정상적인 추천 보류와 처리 실패를 구분한다. 입력정보와 결과를 함께 지우는 기능을 제공한다.
- 다른 기기에서의 기록 동기화는 제공하지 않으며 브라우저 데이터를 삭제하면 기록이 사라진다.
- 서버 설정 파일에서 후보 노출 개수를 1 / 2 / 3 중 선택한다. 기본값 3, 두 유형에 공통 적용하며 재배포로 반영한다. 별도 관리자 화면은 만들지 않는다.
- 최대 3개를 확보한 뒤 순위순으로 설정 개수만 전달한다. 비공개 후보는 브라우저에 보내거나 회상문을 생성하지 않는다.

### 승인된 운영 저장소의 최소 설계

목적은 회상문 API 비용·호출 횟수 집계와 예산 초과·중복 호출 방지다. 기존 저장소에 PostgreSQL 및 `postgres` 의존성이 있으므로 이를 활용해 Neon PostgreSQL에 연결하는 방향으로 설계한다. 로컬 개발 DB가 이미 운영 환경에 배포돼 있다고 가정하지 않으며, 구체적인 리전·접속 설정·마이그레이션은 백엔드 ADR을 따른다.

보관 항목은 두 묶음으로 제한한다.

| 구분 | 보관 항목 | 용도 |
| --- | --- | --- |
| 일별 사용량 | 한국시간 기준 날짜, 실제 API 호출 시도 횟수, 성공·실패 횟수, 사용 토큰, 확정 비용, 예약 중 비용 | 일 한도 및 해당 월의 일별 집계 합산으로 월 한도 검사 |
| 요청 예약·정산 | 무작위 요청 식별자, 최초 요청과 재시도의 연결, 모델·요금 버전, 예약 금액, 실제 사용량·정산 금액, 진행·완료·실패·청구 미확인 상태, 시각 | 중복 실행 방지, 동시 호출 제한, 재시도 추적과 정산 |

프롬프트 원문·모델 응답 본문·개인 이름·출생정보는 이 테이블에 저장하지 않는다. 오류도 개인정보가 섞일 수 있는 전체 메시지 대신 허용된 오류 코드로 기록한다. 비용은 부동소수점 반올림 누적을 피할 수 있는 정확한 금액 표현으로 저장한다.

예산 확인·예약은 짧은 DB 트랜잭션에서 일·월 한도와 동시 실행 수를 함께 검사하고 원자적으로 수행한다. 외부 AI 호출 중에는 DB 트랜잭션을 유지하지 않는다. 호출 전 거절은 실제 API 호출 횟수에 포함하지 않으며, 외부 전송 여부가 불확실한 장애는 호출 시도·비용을 보수적으로 기록한다. 프로세스 종료·응답 유실의 예약 복구·정산과 보존 기간은 백엔드 ADR과 API 계약을 따른다.

개인 기록의 브라우저 저장과 운영 집계의 서버 저장은 별개의 책임이다. 운영 저장소 장애로 예산을 확인할 수 없으면 신규 AI 호출을 중단하고, 이미 계산한 이름과 브라우저에 저장된 결과는 계속 볼 수 있게 한다.

### 확정된 화면 분위기

사용자가 선택한 방향은 ‘따뜻한 편지·책’이다. 오래 간직한 편지를 읽는 듯한 차분하고 아련한 회상 경험을 지향한다. 따뜻한 미색 배경과 먹색 글씨를 기본으로, 추천 이름을 크게 보여주고 회상문은 여백 있게 배치한다.

모바일 세로 화면에서 입력·이름 확인·회상문 읽기·공유의 순서와 가독성을 먼저 확보한다. 편지의 분위기는 입력값 식별과 버튼 조작을 방해하지 않아야 한다. 최초 글꼴·색·화면 배치·에셋 정책은 §9로 확정한다.

## 9. 입력·화면·저장·공유의 확정 세부 정책

### 입력 경계

- 출생 날짜의 양력 환산일이 1900-01-01부터 서버의 Asia/Seoul 오늘까지여야 한다. 음력은 실제 월·일·윤달 존재와 양력 왕복 변환을 검증한다. 양력 하한에 해당하는 1899년 음력 날짜는 허용하므로 음력 연도 선택기는 변환 범위를 따른다. 양력으로 바꾸면 윤달 선택을 해제한다. 달력 전환으로 날짜를 몰래 변환하거나 잘못된 날짜를 다음 달로 넘기지 않는다.
- 현재 엔진의 날짜 범위는 1900-01-01~2026-12-31이다. 2027년 이후 운영은 지원 범위 확장이 선행돼야 한다. 지원 밖 날짜는 입력 지원 범위 안내로 종료하고 기존 기록을 보존한다. 정상 명리 판정 보류로 저장하지 않는다. 기존 음력 검증기의 원본 연도 1900 제한은 양력 환산일 기준 정책과 다르므로 그대로 복제하지 않는다.
- 정확한 출생시각은 출생지에서 기록한 00:00~23:59의 시·분이다. 오늘 입력한 정확시각이 서버 현재시각보다 미래면 거절한다. 역사적 시간대·서머타임 보정은 엔진 정책을 따르며 현재 KST 오프셋을 모든 출생년도에 강제하지 않는다. 시간 모름은 null이며 임의 정오를 넣지 않는다.
- 국내 시·도와 시·군·구는 packages/bazi-application/src/reference/locations.ts의 kma-2026-07-01-v1 목록과 ID를 채택한다. 대표 좌표는 서버가 결정한다. 현재 행정구역이며 상세 주소·역사적 경계를 뜻하지 않는다. 해외·목록 밖 지역은 지원하지 않고 첫 지역을 사용자의 선택 없이 확정하지 않는다.
- 이름은 앞뒤 공백 제거와 NFC 정규화 후 완성형 한글 음절(U+AC00~U+D7A3)만 허용한다. 성씨 1~2음절, 이름 부분 1~5음절이며 Unicode 코드 포인트로 센다. 영문·숫자·내부 공백·단독 자모·한글/한자 혼합 직접 입력은 해당 칸에서 오류로 알린다. IME 조합 완료 후 검증한다.
- 한자는 음절별 선택값 또는 미입력으로 보존한다. 자형·독음 확인을 통과한 것만 선택 가능하며 미검토 뜻·오행은 만들어내지 않는다. 한글을 수정하면 해당 성씨/이름 필드의 기존 한자 선택을 비운다. 추천용 200자 밖 현재 이름도 검색·입력 대상이며 자료가 없으면 한글만으로 계속한다.
- 대운·세운은 제공하지 않아 명리 계산용 성별을 수집하지 않는다. 분위기 선택으로 성별을 추론하지 않는다. 기존 출생정보 앱의 필수 성별·대략 시각 DTO를 그대로 재사용하지 않는다.

### 모바일 화면과 조작

1. 시작: 제품 질문, ‘내 이름 살펴보기’, 저장 기록이 있으면 ‘지난 이름 이야기 이어보기’. 전통 해석에 따른 자기 탐색이며 실제 과거·미래의 증명이 아니라는 짧은 안내를 둔다.
2. 출생정보: 생년월일·양음력/윤달 → 정확시각/모름 → 국내 지역의 순서로 묶는다. 다음 버튼은 첫 오류로 초점을 옮긴다.
3. 현재 이름: 성씨/이름, 음절별 선택 한자, 분위기 기본 ‘상관없음’. 한자를 몰라도 계속할 수 있음을 필드 옆에 표시한다.
4. 입력 확인: 항목별 수정과 ‘지금 이름 살펴보기’로 분석. 처리 중에는 중복 제출을 막고 진행 상태를 알린다. 가짜 퍼센트나 성공을 예고하지 않는다.
5. 현재 이름: 3단계 또는 부분 풀이/보류, 확인된 뜻·소리와 평가 범위. ‘좋은 이름 확인하기’로 균형형 첫 후보를 연다. 보류 시 §4의 행동을 따른다.
6. 추천 이름: 이름·한자·뜻·근거를 먼저 표시하고 아래에 해당 후보 회상문을 지연 생성한다. ‘나의 장점을 극대화하는 이름’은 다른 목적임을 설명한 별도 유형 전환이다. 여러 후보는 번호와 ‘다른 이름 보기’로 이동한다. 비공개 후보를 빈 카드로 만들지 않는다.

휠은 터치 스크롤 모양을 유지하며 키보드 방향키·Enter/Space와 읽을 수 있는 선택값을 제공한다. 한자 선택은 음절 버튼으로 여는 dialog에서 해당 독음·한자·확인된 뜻을 검색/선택한다. 직접 입력한 한자를 미검증 확정하지 않는다. dialog는 제목·닫기·Esc·초점 가두기·호출 버튼으로 초점 복귀와 모바일 세로 스크롤을 제공한다. 브라우저 alert/confirm을 주 입력 UI로 사용하지 않는다. 기록 삭제는 ‘이 브라우저의 입력과 결과를 모두 지울까요?’와 취소/삭제 버튼으로 확인한다.

주 조작은 최소 44×44 CSS px, 본문 16px 이상, 레이블·오류 연결·포커스·상태 알림을 제공한다. 320px 폭에서 가로 스크롤 없이 조작한다. 고정 버튼은 키보드·safe-area와 마지막 내용 공간을 고려한다. 짧은 불투명도 전환만 사용하고 동작 줄이기에서는 제거한다. PC는 최대 720px 읽기 폭을 유지하고 폼 묶음만 넓힌다.

### 따뜻한 편지·책 디자인

최초 토큰은 배경 #F7F2E8, 카드 #FFFCF6, 본문 #292720, 보조문 #625C50, 강조/주 버튼 #665438, 경계 #D5CBBB다. OS 기본 system-ui, -apple-system, BlinkMacSystemFont, Segoe UI, sans-serif를 사용한다. 제목 28~36px, 추천 이름 36~48px, 본문 16~18px/행간 1.7, 8px 배수 여백을 둔다. 색만으로 등급·실패·선택을 구분하지 않는다. 실제 대비와 가독성은 구현 때 확인한다.

외부 폰트·사진·종이 질감 이미지는 추가하지 않는다. CSS 배경·얇은 선·여백으로 분위기를 낸다. 이후 에셋은 출처·라이선스·재배포 조건을 기록한 뒤 도입한다. 시스템 폰트를 별도 파일로 재배포하지 않는다.

### 결과와 실패의 문구

3단계는 **이름 부분의 자원오행 적합성**이며 성씨는 별도 풀이한다. 성씨를 포함한 모든 한자 확인을 평가 전제로 유지한다. 발음과 수리는 별도 참고이며 종합 점수를 만들지 않는다. 조건표는 핵심 규칙 §3을 따른다.

- 잘 맞음: ‘지금 이름에도 균형을 돕는 뜻이 담겨 있어요.’ 대안을 더 좋은 이름으로 단정하지 않는다.
- 일부 보완: ‘지금 이름의 뜻을 살피면서, 보완할 방향도 함께 찾아봤어요.’
- 보완 필요: ‘균형을 보완하는 관점에서 다른 뜻을 더해 볼 여지가 있어요.’ 비권장 글자와 이유를 설명하되 나쁜 이름·불행·개명 필요를 단정하지 않는다.
- 부분 풀이: ‘확인한 소리와 뜻부터 살펴볼게요.’ 빠진 자료와 제외한 평가를 밝히고 한자 미입력을 감점하지 않는다.
- 적합한 후보 부족: ‘현재 검토된 이름 중 조건에 맞는 후보를 찾지 못했어요.’ 분석 불가와 데이터 부족을 구분한다. 조건을 완화하거나 임의 후보로 채우지 않는다.
- 통신/처리 실패: 실제 오류에 맞춰 ‘이름을 살피는 중 연결이 끊겼어요. 입력은 그대로 두었어요.’처럼 알리고 재시도한다. 실패를 정상 보류로 저장하지 않는다.
- 회상문 실패: ‘이름과 뜻은 준비됐어요. 이야기를 불러오지 못했어요.’ 허용된 재시도만 제공하고 예산 제한은 해제 시점을 안내한다.

회상문을 처음 열기 전에 ‘이야기를 만들기 위해 추천 이름·한자 뜻·분석 요약·연령대를 DeepSeek에 보내요. 출생일시 원문은 보내지 않아요’를 알린다. 우리 서버의 개인 기록 비보관을 외부 제공자의 비보관으로 확대해 설명하지 않으며 ‘어디에도 저장하지 않아요’라고 쓰지 않는다. 제공자의 실제 보관·처리 조건은 출시 전에 확인한다.

### 한 사람의 브라우저 기록

완료 입력·결과·공개 후보·성공 회상문을 localStorage의 한 묶음으로 저장한다. 구조·분석·규칙·데이터 버전과 분석 시각을 보존하고 읽을 때 검증한다. 새 결과 직렬화·저장이 성공할 때만 저장본을 교체한다. 차단·용량 초과·저장 동시성 제어 미지원에서는 현재 화면 결과와 기존 저장본을 유지하고 ‘이 브라우저에 저장하지 못했어요’를 알린다. 구체적 Web Locks와 버전 계약은 프런트엔드 ADR을 따른다.

알 수 없는 구조 버전·손상 기록은 자동 재계산하거나 무조건 지우지 않고 복구 불가 안내와 ‘새로 시작’/‘기록 삭제’를 제공한다. 호환되는 과거 결과는 당시 버전·노출 개수대로 읽는다. 설정을 3에서 1로 바꿔도 이미 저장한 후보 3개를 숨기지 않으며 새 분석부터 1개를 전달한다. 규칙 변경으로 과거 평가를 몰래 바꾸지 않는다.

분석 영수증의 24시간 유효기간이 지나거나 현재 서버가 옛 후보를 검증할 수 없으면 새 회상문에는 명시적 새 분석이 필요하다. 완성된 이름·문장은 계속 읽는다. 입력 수정·새 분석 진행 중에는 마지막 완료 기록을 보존하며 전부 보류도 정상 완료일 때 교체한다. 저장 실패는 분석 결과 자체의 실패가 아니다.

새 분석·삭제 이후 도착한 과거 응답과 다른 탭의 오래된 생성 응답이 최신 기록을 덮지 않게 한다. 결과본문을 서버에 보관하지 않으므로 응답 유실 시 동일 작업을 자동 재호출하지 않는다. 서버 계약에 따라 사용자 새 시도 1회만 허용한다. 삭제는 브라우저 개인 기록을 지우며 서버의 익명 비용·횟수 기록 삭제를 뜻하지 않는다. 기기 동기화·계정 보관·기록 목록은 범위 밖이다.

### 친구에게 보내기

‘친구한테 보내기’는 Kakao JavaScript SDK의 Kakao.Share.sendDefault() 텍스트 기본 템플릿으로 서비스 시작 URL을 보낸다. 문구는 ‘나의 이름은 — 내 이름에 담긴 뜻과 또 다른 이름의 이야기를 만나보세요.’로 고정한다. 수신자는 자기 정보를 입력한다. 개인 이름·출생정보·평가·결과 ID를 URL·본문·OG·이미지에 넣지 않는다. OG는 서비스 공통 제목·설명만 사용한다.

별도 카카오 로그인이나 친구 목록 수집은 하지 않는다. 앱·도메인·JavaScript 키 설정 후 사용자의 클릭으로 공유 창을 연다. SDK 차단·미지원·실패 시 시작 URL 복사를 제공하고 복사가 막히면 선택 가능한 URL을 표시한다. 취소를 전송 성공으로 표시하지 않는다. OS 공유 시트는 카카오톡 선택을 보장하지 못하므로 기본 경로를 대체하지 않는다.

채택 근거: [카카오 공식 JavaScript 공유 문서](https://developers.kakao.com/docs/ko/kakaotalk-share/js-link)의 직접 만든 버튼·텍스트 기본 템플릿 지원(2026-09-29 확인). 외부 SDK·도메인 설정 비용을 감수하고 카카오에 보내려는 제품 요구를 충족한다. 실제 전송·배포 검증은 아직 하지 않았다.
