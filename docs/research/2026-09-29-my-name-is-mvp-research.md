# ‘나의 이름은’ MVP — 규칙·데이터 조사

조사일: 2026-09-29. 범위: 저장소의 실제 데이터·코드 및 외부 1차 자료. 제품 코드 수정·모델 호출·DB 변경·테스트 실행은 하지 않았다. 아래 수치는 로컬 JSON 집계 결과이며 외부 전수 검증 결과가 아니다.

제품 결정은 [기획 초안](../specs/2026-09-29-my-name-is-mvp-design.md)을 따른다. 조사에서 제시한 채택안은 기존 결정을 자동으로 바꾸거나 구현 완료를 선언하지 않는다.

후속 실제 대조(2026-09-30): [명리 개별 조건표](2026-09-30-name-mvp-bazi-condition-tables.md), [한자 필드별 검증](2026-09-30-name-mvp-hanja-verification.md), [81수 원전·산식 검증](2026-09-30-name-mvp-suri-verification.md). 아래는 9월 29일 조사 기록이며 최신 검토 상태는 후속 자료와 핵심 규칙 §4·6을 따른다.

## 1. 조사 결론

사주 네 기둥 계산과 이름 검색의 기반은 있으나, 승인된 B 방식의 이름 추천이 이미 완성된 상태는 아니다. 가장 큰 작업은 UI가 아니라 **구조상 오행 강도·보완 방향의 판정 규칙 확정**과 **추천용 한자별 근거 확인**이다.

다음 세 가지를 분리해야 한다.

1. 공적 자료가 확인하는 글자와 독음.
2. 특정 사전·전통 판정 방식에 따른 뜻·획수·오행 해석.
3. MyLife가 선택한 추천 순위·동률·보류·표현 정책.

제품의 회상문은 이름과 분석에 기반한 가상 이야기다. 고전이나 작명 규칙의 존재만으로 이름이 실제 과거·미래의 결과를 바꾼다는 효과가 검증된 것으로 설명할 수 없다.

모든 레코드의 필드 합집합은 `hanja_char`, `hangul_sound`, `meaning`, `original_stroke_count`, `element_five`, `is_forbidden`, `forbidden_reason`이다. 글자별 출처·원본 판본·오행 분류 근거·검토자·검토일 필드는 없다. 680건은 의미가 틀렸다고 전부 확정한 수치가 아니라, 뜻 풀이로 사용할 정보가 충분한지 우선 검토할 대상이다. 양의 획수가 존재한다는 사실도 해당 원획수가 맞다는 뜻은 아니다.

Git의 `1e72ec4`(2026-09-01)는 ‘9,495자 전수’라는 커밋 제목을 사용한다. 현재 고유 문자열 수는 9,494다. [기존 룰북](https://github.com/Seong-Park/mylife/blob/9c3566c61ae18c1c0884d07dff8aa48657bbd58a/docs/04_03_naming_stroke_and_suri_rules.md)과 [파이프라인 문서](https://github.com/Seong-Park/mylife/blob/9c3566c61ae18c1c0884d07dff8aa48657bbd58a/docs/05_03_naming_pipeline_and_hanja_filter.md)는 여전히 8,189자를 언급한다. 숫자의 차이만으로 빠진 공식 글자를 특정할 수 없으며, 현행 공적 목록과 글자·독음 단위 대조가 필요하다.

[기존 테스트](https://github.com/Seong-Park/mylife/blob/9c3566c61ae18c1c0884d07dff8aa48657bbd58a/packages/core-engine/tests/hanjaSearchEngine.test.ts)는 `webhanja.db`를 언급하지만, 이번 저장소 파일 탐색에서는 해당 원본 DB와 추출 스크립트를 찾지 못했다. 테스트의 대표값·최소 개수 검사와 ‘공식 100% 일치’라는 제목을 전수 출처 검증 증거로 간주하면 안 된다.

## 4. 사주 분석 기반의 실제 공백

[Bazi 구현 추적](../references/mylife/docs/bazi/IMPLEMENTATION_TRACKER.md)은 M3 네 기둥 계산과 M4~M7 분석을 구분한다. 현재 승인된 [ADR-004](../references/mylife/docs/bazi/adr/ADR-004-strength-model.md)는 일간 중심의 계절·통근·생조·극설모 관측 원칙이고, 다섯 오행을 전부 비교해 최강을 고르는 완성된 판정표가 아니다.

[레거시 용신 코드](https://github.com/Seong-Park/mylife/blob/9c3566c61ae18c1c0884d07dff8aa48657bbd58a/packages/core-engine/src/saju/yongshin.ts)는 겨울/여름과 수치 임계값으로 fire/water를 선택하고 일부 반환값은 오행이 아니라 십성 범주다. ‘겨울이면 자동 火’ 등을 금지하고 충돌·미평가를 보존하는 [ADR-006](../references/mylife/docs/bazi/adr/ADR-006-yongshin-priority.md)과 다르다. 기존 함수가 있다는 이유로 B 방식의 완성 엔진으로 재사용하지 않는다.

**시간 미상은 추가 후보 분석이 필요하다.** [M3 결과 타입](../../packages/bazi-domain/src/chart/calculation.ts)과 [실제 파이프라인](../../packages/bazi-engine/src/pipeline/calculateFourPillars.ts)은 unknown의 시주를 unavailable로 반환한다. [시간 정규화](../../packages/bazi-domain/src/birth/normalization.ts)에는 실제 시간 구간이 보존돼 있으므로 이를 재사용할 기반은 있지만, 완전한 네 기둥 후보 목록이나 후보 간 구조 판정 합의 결과가 이미 제공되는 것은 아니다.

후속 구현은 실제 구간의 시주·일계·절입 전환 및 공급자 불확실성을 보존한 전체 명식 후보가 필요하다. 독립적인 연·월·일 후보를 무작정 곱하거나 정오를 임의 대입해서는 안 된다. 모든 후보의 목표가 같고 해당 이름 조합도 모두에 적용 가능한지 확인해야 한다. 한 후보가 미평가·미지원인데 나머지만 합치한다는 이유로 제공하면 승인된 보류 정책에 어긋난다.

## 5. 채택을 권하는 최소 규칙 경계

아래는 조사 후 제안이며 자동 승인된 규칙표가 아니다.

1. **원국 관측과 판정을 분리한다.** 확정된 역법·팔자·표는 재사용하고, 월령·통근·투간·생극 관계는 근거와 함께 계산한다. 점수·가중치를 임의로 더해 B 방식이라고 부르지 않는다.
2. **균형형은 검증한 적용 조건에서만 추천한다.** 방법별 적용 가능·미지원·충돌을 보존한다. 모든 기준이 일치한 경우와 명시적 조정 규칙으로 해결한 경우를 구분한다. 미구현 방법을 ‘해당 없음’으로 바꾸지 않는다.
3. **극대화형은 별도의 오행 비교 규칙을 둔다.** 오행별 강도 근거를 남기고, 공동 최강인 경우에만 승인된 화→수→목→토→금 규칙을 적용한다. 관측 축이 서로 엇갈린 경우를 임의 동률로 취급하지 않는다.
4. **공식 허용 목록과 추천용 검토 목록을 구분한다.** 입력 한자 검색은 지정 독음 확인이 중심이다. 추천에는 뜻·원획·자원오행의 채택 근거가 확인된 글자만 사용한다. 이는 한글 이름 목록으로 후보를 제한하는 제안이 아니다.
5. **한자가 없는 현재 이름은 평가 범위를 명시한다.** 음운 평가를 자원오행 종합평가처럼 말하지 않는다. 부분 한자는 확인된 범위만 해설하고, 미입력 글자를 임의로 대체하거나 감점하지 않는다. 3단계 최종 평가를 낼 충분조건은 별도 승인 규칙이 필요하다.
6. **81수리는 적용 가능한 이름 길이에만 참고로 제공한다.** 한글 이름 3~5자 입력 자체는 지원하되, 4격 계산 공식이 채택되지 않은 길이는 수리 항목만 ‘미적용’으로 처리하는 안을 권한다.
7. **자연스러움과 분위기는 제품 기준으로 관리한다.** 나쁜 뜻·비속어를 글자 단위의 광범위한 부분 문자열로 판정하지 않는다. 기존 전통 불용문자나 성별 키워드를 현재 이름에 대한 부정 판정으로 전용하지 않는다.
8. **후보 선택은 최종 이름 조합에서 확인한다.** 목표 오행을 가진 한자 하나가 포함된다는 이유만으로 다른 글자의 영향을 무시하지 않는다. 한자·독음 순서와 성씨를 포함한 최종 조합을 평가한다. 검증된 전수 검색 또는 같은 순위를 보장하는 검색 최적화가 필요하다.

## 6. 데이터 채택 절차와 필요한 산출물

| 순서 | 산출물 | 통과 기준 |
| --- | --- | --- |
| 1 | 원자료 등록부 | 기관·판본·기준일·URL·입수일·해시·재사용 조건 기록 |
| 2 | 글자+독음 대조표 | 현행 허용 목록과 대조하고 이체자·여러 독음 차이를 보존 |
| 3 | 글자별 보강 근거 | 뜻·획수 방식·오행 분류별 출처·검토 상태; 모르면 unknown |
| 4 | 추천용 검토 집합 | 뜻·독음·오행 필수 검토, 수리 표시 시 획수 추가 검토 |
| 5 | 버전별 규칙표 | 입력·적용 조건·판정 결과·반례·보류 조건이 있는 규칙 |
| 6 | 독립 기준 사례 | 구현의 출력으로 기대값을 만들지 않고 사람이 근거와 함께 확정 |

대법원 목록에 있다는 것과 성명학적으로 좋다는 것은 다른 조건이다. 외부 사전의 뜻풀이·편집물 전체를 복제할 권한도 별도로 확인한다. 원자료를 확인하지 않은 채 데이터의 `isSupremeCourt`·출처·검토 완료 상태를 일괄 true로 채우지 않는다.

## 7. 구현 전에 확보할 검증 사례

실행하거나 추가한 테스트가 아니라 후속 구현의 수용 조건이다.

- 같은 팔자 글자 수지만 계절·통근이 다른 사례, 일간 강약과 전체 최강 오행이 다른 사례.
- 공동 최강의 화·수 및 목·금 사례, 동률과 판정 충돌이 구분되는 사례.
- 겨울이라는 이유만으로 火가 자동 선택되지 않는 사례와 미지원 특수 구조.
- 시간 미상에서 모든 전체 명식 후보가 합치하는 사례·갈리는 사례·일부 미지원 사례.
- 한자 없음·부분 입력·모름, 성씨 독음 다중 선택, 복성, 현재 이름 3~5자.
- AB와 BA가 다른 이름으로 검토되는 사례, 한자와 한글 독음 불일치 거절.
- 목표 오행이 바뀌면 추천 근거도 바뀌고 같은 입력·버전이면 후보 순서가 유지되는 사례.
- 데이터 원본 정렬 순서에 의존한 임의 조기 중단이 결과를 바꾸지 않는지 확인.
- 균형형만 보류/극대화형만 보류/둘 다 보류, 후보 0/1/2/3개와 부분 회상문 실패.
- 3단계 현재 이름 평가가 어떤 근거에서 나왔는지 추적 가능하고, 정보 누락이 나쁜 이름으로 바뀌지 않는지 확인.

## 8. 범위와 한계

이번 조사는 전수 한자 감수나 신강신약·용희기의 완성 규칙표 제작을 끝낸 작업이 아니다. 기존 데이터의 정량 상태·재사용 위험·외부 근거의 경계를 확인하고 다음 산출물을 정한 작업이다. 핵심 판정에 대한 독립 기준 사례와 자원오행 분류 근거가 확보되기 전에는 ‘회색 영역이 없는 구현 명세’라고 표현할 수 없다.

확인한 로컬 작업: JSON 필드·개수 집계, 두 사전 해시 비교, 관련 소스·문서·기존 테스트 내용 열람, 사전 변경 커밋 기록 확인. 제품 코드·기존 사전·기존 ADR은 수정하지 않았다.
